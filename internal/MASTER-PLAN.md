# 마스터 플랜 — 비공개

> 이 문서는 배포되지 않습니다. 판단 근거를 남겨두는 곳입니다.
> 액션 아이템의 상태는 `tasks.json`, 진행률은 `make plan`.

## 1. 정리하신 플로우에 대한 검토

방향은 맞습니다. 다만 **세 가지**를 먼저 짚어야 합니다.

### ⚠️ 문제 1 — 레이더 6축은 지금 설계로는 변별력이 안 나옵니다

제안하신 6축:
IC 교통량 · 국토 개발계획 · 주변 도시 인구 · 용도지역/지구 · 중대기업 분포 · 도로

**이 축들은 서로 강하게 상관됩니다.**
인구 많은 곳 → 교통량 많음 → 대기업 많음 → 도로 좋음 → 개발계획 많음.
사실상 "수도권 근접도"라는 **하나의 요인**이 여섯 번 반복됩니다.

그러면 레이더 차트가 이렇게 됩니다.

```
좋은 땅:  ●━━━━━━●        나쁜 땅:  ●━●
         ╱        ╲                ╱   ╲
        ●          ●              ●     ●     ← 둘 다 정육각형
         ╲        ╱                ╲   ╱         크기만 다름
          ●━━━━━━●                  ●━●
```

**모든 매물이 크기만 다른 정육각형**으로 나옵니다.
"이 땅은 교통은 좋은데 인구가 약하다" 같은 **모양의 차이가 안 생깁니다.**
레이더 차트를 쓰는 이유가 사라집니다.

#### 해결 — 축을 "수준"이 아니라 "잔차"로

각 축을 절대 수준이 아니라 **다른 축으로 설명되지 않는 부분**으로 정의합니다.

| 나쁜 축 | 좋은 축 |
|---|---|
| 교통량 (수준) | **교통량 증가율** — 인구 대비 초과분 |
| 인구 (수준) | **인구 증가율** |
| 대기업 수 | **최근 3년 신규 사업장 순증** |
| 개발계획 유무 | **최근 5년 신규 고시 건수** |
| 도로 등급 | **IC 접근성** (거리 밴드) |
| 용도지역 | **개발 여력** = 법정 건폐율 − 현재 이용률 |

전부 **변화량·잔차**라 서로 덜 상관됩니다. 그래야 모양이 갈립니다.

> 이건 이미 `docs/hypothesis.md` 에서 "수준 상관은 수도권 효과일 뿐"이라고
> 정리한 것과 **같은 문제**입니다. 레이더에서도 똑같이 발생합니다.

#### 해결 — 종합점수는 만들지 않습니다

6축 평균을 내면 "종합 85점" 같은 게 나오는데,
**그 가중치에는 근거가 없고**, 투자 권유로 읽히면 법적 리스크입니다
(`docs/legal-notes.md` §3).

축별 백분위만 보여주고, 종합 순위는 매기지 않습니다.

### ⚠️ 문제 2 — 가장 큰 데이터 누락: 개별공시지가

실거래는 **희소합니다.** 어떤 필지는 10년간 한 번도 거래되지 않습니다.
그러면 매물의 90%에 점수를 못 매깁니다.

**개별공시지가는 모든 필지에 매년 있습니다.**

| | 실거래가 | 개별공시지가 |
|---|---|---|
| 커버리지 | 거래된 필지만 | **전 필지** |
| 주기 | 비정기 | 매년 1월 1일 |
| 성격 | 실제 시장가 | 과세 기준가 (시세보다 낮음) |
| 쓰임 | 절대 가격 수준 | **모든 필지의 시계열 baseline** |

두 개를 같이 써야 합니다.
- 실거래 = 그 지역의 **시세 수준**
- 공시지가 = 개별 필지의 **상대적 위치와 추세**

이게 빠지면 "매물마다 레이더를 그린다"가 성립하지 않습니다.

### ⚠️ 문제 3 — 순서가 뒤집혀 있습니다

계획하신 순서는 **데이터 전부 → 레이더 → 회원**입니다.
이러면 첫 사용자를 만나기까지 몇 달이 걸리고,
**레이더 6축이 쓸모 있는지는 그때 가서야** 알게 됩니다.

그런데 지금 **9월 7일 마감 무료 진단 이벤트**가 돌고 있습니다.
여기 신청하는 사람들은 **"토지를 보고 있고, 판단을 도와달라는" 정확한 타깃**입니다.

> **이 20명이 첫 사용자 인터뷰 집단입니다. 이걸 안 쓰는 게 가장 큰 기회 손실입니다.**

#### 역순 제안

1. 이벤트 신청자에게 **수기로 진단**해 드립니다 (원래 약속한 것)
2. 진단하면서 **"내가 실제로 무엇을 보는지"** 를 기록합니다
   → 그게 레이더 축의 진짜 정의가 됩니다. 추측이 아니라 관찰입니다
3. 그중 **가장 자주 본 2~3개 축**만 먼저 자동화합니다
4. 그 20명에게 다시 보여주고 반응을 봅니다
5. 반응이 있는 축만 남기고 확장합니다

6축을 다 만들어놓고 "안 쓰네" 하는 것보다 훨씬 빠릅니다.

## 2. 빠진 항목

### 데이터

| 항목 | 왜 필요한가 | 소스 |
|---|---|---|
| **개별공시지가 시계열** | 전 필지 baseline. 없으면 대부분 매물에 점수 못 매김 | 부동산공시가격 알리미 / data.go.kr |
| **지가변동률** | 분기별 시군구 단위 추세 | 한국부동산원 |
| **토지이용계획 조회 API** | 용도지역·지구를 매물마다 자동 판정 | 토지이음 / LURIS |
| **연속지적도** | 지도에 필지 경계를 그리려면 필요 | VWorld |
| **건축물대장** | 공장·창고의 연면적·용도·사용승인일 | 국토부 건축물대장 API |
| **공장등록 현황** | "중·대기업 분포"의 실제 소스 | **팩토리온** (factoryon.go.kr) |
| **전국사업체조사** | 사업체 수·종사자 수 (시군구·읍면동) | KOSIS |
| **주민등록 인구** | "주변 도시 인구" 축 | 행안부 / KOSIS |
| **표준노드링크** | "도로" 축을 실제로 계산하려면 도로망이 필요 | 국가교통정보센터 |
| **수치표고모델(DEM)** | 경사도 자동 판정 | 국토지리정보원 |
| **산업단지·택지 고시일** | 개발계획 축의 t=0 | KICOX / LH / 관보 |

> **"중·대기업 사업장 주소"** 는 공개 소스가 마땅치 않습니다.
> DART는 상장사만, 고용보험은 비공개입니다.
> **팩토리온 공장등록 데이터**가 가장 가깝습니다 — 공장 매물이 타깃이므로 오히려 잘 맞습니다.

### 제품 기능

| 빠진 것 | 왜 |
|---|---|
| **매물 검색·필터** | 지역·가격·면적·용도지역·점수. 매물이 쌓이면 필수 |
| **관심 매물 저장** | 사용자 회원가입의 이유가 됩니다. 이게 없으면 가입할 이유가 없음 |
| **신규 매물·신규 고시 알림** | 재방문을 만드는 유일한 장치 |
| **문의 → 중개사 연결 (리드)** | **등록 수수료보다 클 수 있는 수익원** |
| **허위매물 신고** | 공인중개사법상 모니터링 의무 |
| **관리자 화면** | 중개사 승인·매물 검수·신고 처리. 사람이 해야 하는 일 |
| **조회 로그** | 어떤 매물이 얼마나 조회됐는지 — 중개사에게 파는 정보가 됨 |

### 회원 관리에서 빠진 것

- **관리자 역할** — 사용자/중개사 둘만 있고 운영자가 없음
- **카카오 로그인** — 한국 서비스에서 사실상 필수
- 이메일 인증 · 비밀번호 재설정
- **탈퇴 및 개인정보 삭제** — 개인정보보호법상 의무
- 중개사 자격 검증 (`docs/listings-api.md` 에 이미 정리)

## 3. 수익 모델 재검토

계획은 **중개사 등록 수수료**입니다. 문제가 하나 있습니다.

> **매물이 없으면 사용자가 안 오고, 사용자가 없으면 중개사가 돈을 안 냅니다.**

닭과 달걀입니다. 순서를 이렇게 잡는 편이 낫습니다.

| 단계 | 중개사에게 | 사용자에게 | 수익 |
|---|---|---|---|
| 1 | **무료 등록** | 분석 + 매물 열람 | 없음 |
| 2 | 무료 등록 + **조회수 리포트** | 관심 매물·알림 | 없음 |
| 3 | 무료 등록 + **상단 노출 유료** | 〃 | 노출 광고비 |
| 4 | 〃 + **문의 리드 과금** | 〃 | 리드 + 광고 |
| 5 | 등록 수수료 도입 | 〃 | 전부 |

**1단계에서 돈을 받으면 매물이 안 모입니다.**
먼저 무료로 채우고, 사용자 트래픽이 생긴 뒤에 과금해야 합니다.

## 4. 저장소·서버 결정

이미 `docs/who-does-what.md` 트랙 B 에서 정리한 대로 **Supabase** 를 권합니다.

| | |
|---|---|
| DB | Supabase Postgres + **PostGIS** (거리·반경을 DB 인덱스로) |
| 인증 | Supabase Auth (이메일 + 카카오) |
| 파일 | Supabase Storage (매물 사진, 중개사 등록증) |
| 권한 | **RLS** — "타인 매물 조회 불가"를 DB 가 강제 |
| 배포 | Vercel (정적) — 상시 서버 없음 |
| 분석 | Python + DuckDB (배치) → 결과만 Postgres 로 |

현재 FastAPI + SQLite 로 만든 매물 API 의 **13개 보안 테스트가 그대로 RLS 정책 명세**가 됩니다. 버려지지 않습니다.

## 5. 단계 구분

| Phase | 목표 | 끝났다고 볼 기준 |
|---|---|---|
| **P0** | 지금 있는 것 정리 | 배포 정상, 이벤트 페이지 가동 |
| **P1** | 첫 사용자 20명 | 수기 진단 완료 + 진단 기준 문서화 |
| **P2** | 데이터 기반 | 파일럿 권역 실데이터로 β 검증 |
| **P3** | 레이더 v1 | 상관 제거된 3축, 20명 반응 확인 |
| **P4** | 회원·매물 | Supabase 이전, 중개사 무료 등록 |
| **P5** | 확장 | 전국 데이터, 6축, 알림 |
| **P6** | 수익화 | 노출·리드 과금 → 등록 수수료 |

각 Phase 의 액션 아이템은 `tasks.json`.
